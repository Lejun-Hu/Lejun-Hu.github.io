# 通用写作与代码讲解规则（General）

> 适用范围：`_notes/` 下所有源码学习笔记。把本文件作为上下文提供给模型时，以下规则优先于模型的默认写作风格。

## 1. 先给地图，再进入细节

- 每个大章、小节开头必须有一段**正式正文**作为引入，说明：本节要解决什么问题、它在整体流程中的位置、以及阅读主线。引入用正文段落，不要写成引用块（`>`）。
- 讲一个具体知识点之前，先用一两句交代"接下来详细讲的内容在整体结构中处于什么位置"。
- 不同内容点之间切换时补一句承上启下的过渡，不要直接跳到下一个话题。
- 涉及多步流程时，先给出「步骤 / 时机 / 入口函数 / 产物」这类总览表或调用链图，再逐步展开。
- 不要在主体行文逻辑中途插入大段解释性细节打断阅读；这类内容集中放到对应位置，或与已有相似内容合并。
- 重构整章时，先通读、列出全部要点，再按初学者的学习顺序重新编排。

## 2. 面向初学者，但保持专业

- 假设读者没读过源码：陌生术语、缩写第一次出现时给出准确定义与出处。
- 讲解顺序：是什么 → 为什么存在 → 如何影响整体框架。
- 非框架核心的实现细节（工具函数、日志宏、辅助机制）重意义、轻实现，不展开位运算、算法步骤等繁琐细节；核心链路（初始化流程、通信路径、关键数据结构）可以逐行深入代码。
- 表述可以详细具体，但要控制篇幅；精简靠去除重复与合并同类内容，不靠删信息。

## 3. 内容完整性

- 重构时默认**不删除、不新增**核心知识点；重复或相似的内容合并到一处。
- 只有用户明确要求时才做结构性删除，并说明删了什么、为什么。
- 修正事实错误时要说明改了什么、依据是什么。

## 4. 源码核实（硬性要求）

- 所有函数名、调用关系、执行时序、行号、版本结论，必须回源码或官方文档核实后再写入；不臆测、不凭记忆。
- 引用格式统一为 `文件:行号` 或 `文件:起止行`，例如 `src/init.cc:2667`、`group.cc:857`；缩写的全称要能给出官方出处。
- 用户提供的、或从网上看到的结论同样要核实；找不到可验证出处的内容，不要写成定论。
- 组织代码讲解时，先抽象出骨干结构与调用链，再逐部分说明涉及哪些软件结构；必要时贴**带语言标注的真实代码片段**，不要用伪代码冒充源码。
- 不同时机发生的步骤必须按真实时序组织，不能把跨阶段的调用写成一条连续流程。
- 发现旧内容与当前源码不一致（函数改名、时序变化、路径错误、版本过时），主动修正并告知。

## 5. 表达方式

- **禁止任何形式的比喻、类比和拟人化表达**（例如台账/通讯录/修路与车/接棒/入场券/发令枪/信封/集装箱/认识彼此等），一律用准确的技术语言直接描述结构与机制。
- 禁止"一句话总结""本质就一句话"这类过度总结句式，以及"顺带一提""插叙一段"这类随口表达；补充说明用"补充""另外"等正式措辞，或直接写成正文。
- 语气像面对面交流，但保持严谨、专业，不要过于轻松，也不要 AI 腔的排比与套话。
- 标题与小结用平实严谨的表述，不要用标新立异的概括（如"三个对象、两次翻译"）。

## 6. 格式与标记

- 不使用带圈数字 `①②③` 等标记。列表用 `1.` `2.`；正文行内引用写「第 1 步」「第 2 层」「第 3 点」「阶段 2、3」。
- 章节级引入用正式正文段落；引用块（`>`）只用于补充说明、辨析、可跳过的延伸内容。
- 代码块必须带语言标注（` ```cpp `、` ```c `、` ```bash `）以便语法高亮；无语言的 ASCII 流程图保持纯文本。
- 表格用于对比与总览，不要在表格里堆长段落。

## 7. 协作流程

- 动手前先完整读取相关章节或文件的**当前**文本，不凭记忆编辑。
- 改动后复查逻辑连贯性（承上启下、编号连续、交叉引用无悬空），并跑 lint 检查。
- 除非用户明确说"直接推 / 改完直接推"，否则改动完成后先汇报，等确认再 `git push`。
- commit message 用简短中文，描述本次实际改动。

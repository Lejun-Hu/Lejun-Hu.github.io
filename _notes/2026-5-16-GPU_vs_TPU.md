> 过去十几年，GPU 几乎一直是“AI 算力”的代名词。尤其在 2012 年 AlexNet 使用 NVIDIA GTX 580 在 ImageNet 上取得突破之后，基于 CUDA 的 GPU 并行计算迅速成为深度学习的事实标准。从实验室里最早的一批 CNN 模型，到如今上千卡集群训练的大语言模型，绝大部分 AI 工作都建立在 GPU 生态之上。
>
> 但如果把视线再拉远一些，会发现这个格局正在逐渐变化。Google 早在 2015 年就已经在内部部署第一代 TPU，并于 2016 年正式公开这种专门面向 Tensor 运算的 ASIC 架构。随后 TPU v2 开始支持大规模训练，逐渐成为 Google 内部搜索、推荐与 Gemini、PaLM 等超大规模模型的重要基础设施。与此同时，Groq 等公司则进一步把“专用化”推向推理领域，提出了 LPU（Language Processing Unit）这一面向大语言模型推理的数据流架构。尤其在 2023 年之后，随着 LLM 推理延迟与 token throughput 成为新的瓶颈，LPU 开始逐渐进入大众视野。而 NVIDIA 自己也在不断把 GPU 做得越来越不像传统意义上的 GPU。Tensor Core、NVLink、NVSwitch、Transformer Engine 等设计，实际上都在让 GPU 越来越偏向专门为 AI workload 优化的数据流机器。
>
> 三者的演进，实际上指向同一个趋势：AI 计算正在从“通用并行处理器”逐步走向“为张量数据流高度定制化的专用计算系统”。
>
> GPU、TPU、LPU 恰好可以看作这条路线上的三个不同坐标。本文将从架构、内存系统、软件栈、互联扩展、硬件利用率以及设计思路几个维度，认真梳理它们之间的本质区别。

## 一、TPU、GPU、LPU 的架构差异

### GPU：AI 时代最成功的通用并行计算平台


如果你对于计算机体系结构有一些基本了解，我们通常知道，一个现代处理器大致都会由两部分组成：负责执行计算的运算单元，以及负责存放和搬运数据的内存系统。前者包括 ALU（Arithmetic Logic Unit）、FPU（Floating Point Unit）、乘法器、向量运算单元等，后者则包括寄存器、L1/L2/L3 Cache、主存等分级结构。这种“计算单元 + 分级内存”的设计，本质上就是经典冯诺依曼架构在现代处理器中的延续。CPU 之所以强大，很大程度上来自于它对复杂逻辑、分支预测、乱序执行以及低延迟任务的极致优化。

GPU 虽然最早是作为图形处理器诞生的，但它本质上仍然属于这一大类计算机架构。NVIDIA 在 1999 年正式提出 GPU（Graphics Processing Unit）这一概念，最初的目标其实非常直接：加速图形渲染中的海量并行计算。例如像素着色、顶点变换、光栅化，这些工作都具有一个非常鲜明的特点——大量数据执行相同类型的运算。也正因为如此，GPU 从一开始就没有像 CPU 一样，把大量晶体管投入到复杂控制逻辑、超大缓存和超强单线程性能上，而是走向了另一条路线：**用数量极多的小型计算核心，换取超高吞吐量的并行计算能力。** 这也是 GPU 和 CPU 在架构思路上最本质的区别。

CPU 通常只有几十个核心，但每个核心都非常复杂，拥有深流水线、分支预测器、乱序执行引擎以及极大的缓存。而 GPU 则会把芯片面积尽可能让给更多的执行单元。以现代 NVIDIA GPU 为例，整个芯片会被划分为大量 SM（Streaming Multiprocessor，流式多处理器），每个 SM 内部再包含大量 CUDA Core、Tensor Core、寄存器文件、Warp Scheduler 和 Shared Memory。相比 CPU 的“大核”，SM 更像是大量功能相对简单、但吞吐量极高的小型并行计算集群。

这种设计背后，其实对应的是经典的 Amdahl's Law（阿姆达尔定律）。它指出，一个程序能够被并行化加速的上限，最终取决于其中“不可并行”的那部分比例。GPU 的核心假设其实是：**图形处理、矩阵运算以及深度学习中的绝大多数工作，天然具有极高的数据并行性。** 也就是说，只要能把任务拆成足够多的小块，同时喂给大量执行单元，那么整体吞吐量就会远远超过传统 CPU。

理解这一点之后，我们再来看 GPU 内部的结构就会清晰很多。现代 NVIDIA GPU 的核心计算单元是 SM。SM 本身并不是“一个核心”，而更像是一个完整的小型计算簇。一个 SM 内部会包含 CUDA Core、Tensor Core、Warp Scheduler、Load/Store Unit、Register File、Shared Memory / L1 Cache，以及特殊函数单元（SFU）。其中 CUDA Core 负责最基础的标量和向量运算，比如加减乘除、地址计算、控制逻辑等；Tensor Core 则是后来为了 AI 和矩阵乘法专门加入的高吞吐矩阵计算单元；Warp Scheduler 负责线程调度；而 Shared Memory 和寄存器则承担数据缓存和局部数据复用。

*图 1：GPU SM 内部结构*

这里一个特别容易混淆的概念是，很多人会把 CUDA Core、SM、Stream Processor 混在一起。实际上，SM 是一个大的执行集群，CUDA Core 是 SM 内部真正执行标量运算的小执行单元，而 Stream Processor 则是 AMD GPU 对类似 CUDA Core 的称呼。例如 H100 一共有上百个 SM，而每个 SM 内部又包含数十到上百个 CUDA Core。真正执行程序指令的，其实是这些 CUDA Core。

而 CUDA 编程模型中的线程（thread），则并不是“一线程对应一个 CUDA Core”这么简单。GPU 实际执行时，会把线程以 32 个为一组打包成 Warp。Warp 是 NVIDIA GPU 中真正的硬件调度单位。也就是说，Warp Scheduler 并不是单独调度某一个线程，而是一次调度整个 Warp。

这里就引出了 GPU 一个非常核心的设计：SIMT（Single Instruction Multiple Threads）。从表面上看，它很像 SIMD（Single Instruction Multiple Data），即“一条指令处理多个数据”。但两者其实存在重要区别。SIMD 更强调多个数据严格执行同一条指令，而 GPU 的 SIMT 模型则更加灵活。一个 Warp 中的 32 个线程虽然通常会同时执行同一条指令，但每个线程本身仍然拥有独立的程序计数器（Program Counter）、寄存器状态以及线程上下文。这意味着，理论上同一个 Warp 中的不同线程可以执行不同逻辑。

例如下面这样一段 CUDA 代码：

```cpp
if (threadIdx.x < 16) {
    do_A();
} else {
    do_B();
}
```

此时 Warp 会发生所谓的 Warp Divergence（Warp 分歧）。前 16 个线程执行 `do_A()` 时，后 16 个线程实际上会被 mask 掉；随后 GPU 再切换回来执行 `do_B()`。也就是说，虽然逻辑上两个分支都能执行，但在任何一个 cycle 内，实际上只有部分 CUDA Core 真正在工作。因此一旦 Warp 内部出现大量条件分支，性能就会明显下降。

这也是 GPU 和 TPU 在设计上的一个非常重要区别。GPU 的 SIMT 模型，本质上是在 **用部分执行效率，换取更强的通用性。** 因为开发者并不需要每次都严格准备好“刚好适合 Warp Size 的规则数据”，也不需要所有线程永远执行完全相同的逻辑。GPU 可以允许程序中存在一定程度的不规则控制流，而不会直接无法运行。代价则是 Warp Divergence、调度开销、部分执行单元空转、cache miss 以及 runtime 不确定性，这些都会导致 GPU 实际利用率低于理论峰值。

但也正因为这种灵活性，CUDA 编程的门槛其实比很多专用 AI 加速器低得多。开发者可以先把功能跑通，后续再慢慢调优 grid size、block size、occupancy、memory coalescing、shared memory reuse 等性能细节。因此 GPU 的成功，本质上并不仅仅来自硬件性能，还来自于它在“通用性”和“吞吐量”之间找到了一个非常现实的平衡点。

另外一个近年来越来越重要的变化，是 GPU 内部的 Tensor Core 正在变得越来越强，以至于传统的 CUDA Core 反而逐渐退居辅助角色。尤其在 Transformer 成为主流之后，大量 workload 已经变成了标准化矩阵乘法和 attention 计算。为了持续给 Tensor Core 提供数据，NVIDIA 在 Blackwell 架构中进一步加入了 TMEM（Tensor Memory）。TMEM 本质上是一种更加靠近 Tensor Core 的专用片上存储结构，用来减少 Tensor Core 在等待数据时产生的 pipeline bubble。随着 AI workload 越来越规则化，GPU 的内部结构也开始越来越偏向“数据流机器”而非传统图形处理器。这其实也是为什么今天的 GPU，已经越来越不像最早那个为了游戏图形而设计的 GPU 了。


### TPU：为矩阵计算而生的数据流机器
相比 GPU 的历史，TPU 的出现要晚得多。NVIDIA 在 1999 年正式提出 GPU（Graphics Processing Unit）这一概念，当时的主要目标还是加速图形渲染。而 Google 第一代 TPU 则直到 2015 年才开始在内部数据中心部署，并于 2016 年发表在论文《In-Datacenter Performance Analysis of a Tensor Processing Unit》中正式对外公开。从时间线上看，当 TPU 诞生时，GPU 已经经历了十余年的发展，并且凭借 CUDA 生态逐渐成为深度学习训练的事实标准。

但 Google 在大规模部署神经网络之后很快发现，GPU 虽然拥有强大的通用性，却并不一定是执行神经网络最理想的硬件。搜索排序、语音识别、翻译模型等工作负载中，绝大部分时间都消耗在矩阵乘法和张量运算上，而 GPU 中大量用于支持复杂控制流、线程调度、缓存一致性以及图形渲染的硬件，在这些场景下其实很少被真正利用。于是 Google 开始思考一个问题：如果只保留神经网络真正需要的部分，并把所有晶体管都投入到矩阵运算本身，会得到怎样一种处理器？TPU 就是在这种背景下诞生的。

从整体架构来看，TPU 比 GPU 简洁得多。如果把现代 GPU 看作一个拥有上百个 SM、数千个 CUDA Core 的大型并行处理器，那么 TPU 更像是一台专门执行矩阵乘法的数据流机器。以目前广泛部署的 TPU v4 和 TPU v5 系列为例，一个 TPU 芯片通常只包含两个 TensorCore，而不是上百个类似 GPU SM 的执行集群。

![TPU v5e 脉动阵列结构示意图]({{ '/assets/images/notes/TPU.png' | relative_url }})
*图 2：TPU v5e 脉动阵列结构示意图*

这里需要特别说明的是，TPU 的 TensorCore 与 NVIDIA Tensor Core 虽然名字相似，但实际上并不是同一个概念。NVIDIA 的 Tensor Core 是 SM 内部的一个矩阵计算单元，而 TPU 的 TensorCore 则更接近于一个完整的计算核心，其规模远大于单个 GPU Tensor Core，甚至可以看作是一个独立的数据流处理器。如果对应到 GPU 的架构来看，TPU 的一个 TensorCore 大致承担了 GPU 中 Tensor Core 的矩阵计算、Shared Memory 的局部数据缓存、Warp Scheduler 的执行调度以及 Load/Store Unit 的数据搬运等多种功能，只是这些功能在 TPU 中被重新组织成了一个高度专门化的数据流系统。

TPU TensorCore 内部最重要的组件是 MXU（Matrix Multiply Unit），可以认为是整个 TPU 的计算心脏。以 TPU v4 为例，每个 TensorCore 内包含两个 128×128 的 Systolic Array（脉动阵列），总计超过三万个乘加单元同时工作。与 GPU 中由大量 CUDA Core 分散执行矩阵运算不同，TPU 的矩阵计算几乎完全由这些二维阵列完成。在脉动阵列中，数据会像流水一样在阵列内部持续流动。权重矩阵从一个方向进入阵列，激活值从另一个方向进入阵列，每个计算单元只负责执行最简单的乘加操作，然后把结果传递给相邻单元继续处理。整个过程中，数据会在阵列内部被反复复用，而不是频繁访问外部存储。

![TPU v5e 脉动阵列结构示意图]({{ '/assets/images/notes/2TPU.png' | relative_url }})
*图 3：2个组合 TPU 脉动阵列结构示意图*

这种设计最大的优势在于数据搬运成本极低。事实上，在现代芯片中，真正昂贵的往往不是乘法本身，而是把数据搬运到乘法器旁边。Google 在 TPU 的设计中投入了大量面积给片上 SRAM 和数据流控制逻辑，而不是复杂的调度器和缓存系统，其核心目标就是尽可能减少数据移动。这也是 TPU 和 GPU 在架构哲学上的第一次重大分歧。GPU 的思路是提供大量执行单元，再通过 Warp Scheduler、Cache Hierarchy 和运行时调度尽可能把它们喂饱。而 TPU 的思路则是提前规划好数据流，让计算单元永远知道下一拍应该计算什么。

这种差异进一步体现在执行模型上。GPU 采用的是 SIMT（Single Instruction Multiple Threads）模型，Warp 内的线程虽然大多数时间执行同样的指令，但理论上仍然允许不同线程拥有不同控制流，因此 GPU 需要复杂的 Warp Scheduler、Scoreboard 和各种动态调度机制来管理这些线程。TPU 则完全放弃了这种设计，更接近经典的 SIMD（Single Instruction Multiple Data）甚至 Dataflow Machine。编译器会在程序开始执行之前，把整个计算图展开为一个确定的数据流网络。每一份数据何时进入阵列、何时离开阵列、何时从片上存储读取、何时写回 HBM，都在编译阶段提前决定。因此 TPU 中几乎看不到类似 Warp Scheduler 的复杂硬件——它并不需要在运行时决定下一条指令执行什么，因为这些决策早已在编译期间完成。这种设计让 TPU 获得了极高的执行效率，同时也意味着它不擅长处理复杂控制流。对于矩阵乘法、卷积、Attention 等规则计算，TPU 可以接近理论峰值运行；但如果程序中包含大量动态分支、不规则数据结构或者频繁变化的执行路径，GPU 往往会更加灵活。

除了计算单元本身之外，TPU 的内存系统也与 GPU 存在明显差异。GPU 依赖 L1 Cache、L2 Cache 和 Shared Memory 构成的层级缓存体系，希望通过缓存命中来减少访问 HBM 的次数。而 TPU 则更倾向于显式管理数据流。典型 TPU 芯片内部会包含 HBM（High Bandwidth Memory）、VMEM（Vector Memory）、SMEM（Scalar Memory）以及寄存器堆等存储层级。其中 VMEM 本质上是一块容量巨大的片上 SRAM，用于存放即将进入 MXU 的张量数据；SMEM 则主要存放标量和控制信息。数据何时从 HBM 搬运到 VMEM，何时送入 MXU，通常由编译器在生成程序时直接决定，而不是依赖运行时缓存策略。因此从程序员视角来看，GPU 更像一个具有大量缓存和线程调度能力的通用并行处理器，而 TPU 更像一个由编译器控制的数据流系统。

最后回到最开始那个问题：为什么 TPU 只需要两个 TensorCore，而 GPU 却需要上百个 SM？答案其实很简单——因为两者的设计目标完全不同。H100 拥有 132 个 SM，每个 SM 都需要支持线程调度、控制流处理、缓存管理和通用计算，因此单个 SM 的面积和功能相对受限。而 TPU 的 TensorCore 几乎把所有资源都投入到了矩阵计算与数据搬运之中，因此单个核心规模远大于 GPU 的 SM。从单核能力来看，一个 TPU TensorCore 通常远强于单个 GPU SM，但 GPU 可以通过更多 SM 提供更强的通用性和更灵活的资源调度。因此两者最终能够达到的总吞吐量，仍然需要结合具体型号、制程、频率以及工作负载进行比较。

不过从 TPU 的设计中已经能够看到一种非常明显的趋势：随着 AI 工作负载越来越集中于矩阵乘法和张量运算，硬件设计正在逐渐从“通用并行处理器”向“专门的数据流计算机”演化。而 TPU 正是这一趋势最典型的代表之一。


### 三、LPU：进一步走向推理专用化的计算架构

如果说 TPU 已经是在 GPU 基础上进一步削弱通用性、强化矩阵计算能力，那么 LPU（Language Processing Unit）则几乎把这种思路推到了极致。LPU 这个概念由 Groq 提出，这家公司成立于 2016 年，而它最特殊的一点在于，其创始人 Jonathan Ross 正是 Google TPU 项目的核心设计者之一。在参与 TPU 研发之后，Ross 逐渐产生了一个新的判断：即便 TPU 已经大幅提高了神经网络计算效率，但它仍然保留了许多为了兼容训练任务和通用机器学习工作负载而存在的复杂性。而随着大语言模型逐渐成为 AI 的主要形态，未来最重要的问题或许不再是训练，而是推理。

事实上，训练和推理虽然都属于神经网络计算，但两者对于硬件的要求并不完全相同。训练阶段需要执行前向传播、反向传播和梯度更新，需要频繁读写参数、保存中间激活值，并进行大规模梯度同步。而推理阶段则简单得多——模型参数已经固定，系统只需要不断执行“Token 进入、矩阵乘法、下一个 Token 输出”这条持续不断的数据流流水线。尤其对于 Transformer 和大语言模型来说，推理过程中的绝大部分计算最终都会退化为矩阵乘法、Attention 和少量向量运算。Groq 的观点非常激进：如果未来的大部分 AI 计算都会变成推理，那么为什么还要继续为训练能力和通用计算能力支付额外的硬件成本？于是 LPU 被设计出来，从诞生开始就不是训练芯片，几乎完全围绕 LLM 推理构建。Groq 官方甚至直接将其称为“Designed for inference. Not adapted for it.”——它并不是像 GPU 一样后来逐渐适配 AI，也不是像 TPU 一样同时兼顾训练与推理，而是从硅片定义阶段开始，就只服务于推理这一件事情。

从架构上看，LPU 与 GPU、TPU 都存在明显区别。GPU 的核心是大量 SM，TPU 的核心是大型 Systolic Array，而 LPU 更接近一种完全确定性的数据流机器。Groq 官方将其称为“可编程流水线架构”（Programmable Assembly Line Architecture）。在这种架构中，整个模型执行过程会在编译阶段被展开成一个精确的数据流网络，数据会沿着预先规划好的路径持续流动。每一个时钟周期内，哪个计算单元执行什么操作、数据位于什么位置、何时读取、何时写回、何时跨芯片传输，全部提前确定。因此 LPU 内部几乎不存在 GPU 那样复杂的运行时调度逻辑，没有 Warp Scheduler，没有 Cache Miss 处理，没有动态资源竞争，也没有运行时的不确定性。Groq 的设计目标非常明确，就是让每一个时钟周期都被提前规划，这样编译器就能够像规划流水线工厂一样，精确安排整个模型执行过程。

为了实现这一点，LPU 做出的另一个激进选择是大量使用片上 SRAM。在 GPU 中，大部分模型参数最终存放在 HBM 中，即便 HBM 已经拥有数 TB/s 的带宽，但它本质上仍然属于片外存储。而 LPU 则试图把尽可能多的数据直接放在芯片内部。Groq 第一代 LPU 集成了数百 MB 级别的片上 SRAM，并直接将其作为模型权重存储，而不是传统意义上的 Cache。这样做带来的好处非常明显，因为对于现代 AI 芯片来说，真正昂贵的往往不是计算，而是数据搬运。大量能耗其实都消耗在 HBM 到 Cache 再到计算单元之间的数据传输上，而 SRAM 的访问延迟远低于 HBM。当模型参数尽可能驻留在片上之后，计算流水线几乎不需要等待数据到来，这也是为什么 Groq 经常能够实现极高 Token Throughput 的原因之一。

与此同时，LPU 的芯片互联也采用了与 TPU 类似的思路。Groq 并不把多颗芯片视为独立处理器，而是希望让它们共同组成一个更大的逻辑计算核心。数据在芯片之间的传输同样采用静态调度，编译器会提前规划数据从哪颗芯片发送、哪颗芯片接收、何时到达、何时开始下一步计算，因此其网络本身也是确定性的。从某种意义上来说，LPU 已经越来越不像传统意义上的处理器，它更像是一台专门执行 Transformer 推理的数据流机器。

当然，这种极端专用化也意味着明显的代价。首先，LPU 几乎无法承担训练任务，训练过程中的梯度更新、优化器状态、动态内存分配以及反向传播，都会破坏这种高度确定的数据流结构。因此目前 Groq 的定位非常明确：GPU 和 TPU 负责训练，LPU 负责推理。其次，当未来模型结构发生重大变化时，LPU 的适应能力也天然弱于 GPU。GPU 的强项始终在于通用性，即便出现全新的网络结构，开发者通常只需要重新编写 Kernel 即可运行，而 LPU 的许多性能优势，本质上都建立在 Transformer 与大语言模型高度规则的数据流之上。

因此从 GPU 到 TPU，再到 LPU，其实能够看到一条非常清晰的演进路线。GPU 是通用并行计算平台，TPU 是面向张量计算的数据流机器，而 LPU 则进一步成为面向大语言模型推理的专用计算系统。它们并不是简单的迭代关系，而是在 AI 时代对于“究竟应该保留多少通用性”这个问题，给出了三种完全不同的答案。


## 二、GPU 与 TPU 的软件栈差异

在上文中，我们已经从硬件架构设计的角度理解了 GPU、TPU 与 LPU 三种硬件的区别。但对于大多数软件工程师或者模型工程师而言，真正接触硬件的机会其实并不多。更多时候，我们面对的是 PyTorch、JAX、TensorFlow 等 AI 框架，以及模型代码、训练脚本和推理服务。那么，一个简单的矩阵乘法究竟是如何从几行 Python 代码，最终变成硬件中数万个计算单元同时执行的乘加操作的？GPU、TPU 与 LPU 在这个过程中又有什么本质区别？理解这一点，实际上比单纯理解硬件架构更加重要，因为现代 AI 系统的性能，很大程度上已经不再由硬件本身决定，而是由软件栈如何组织和调度硬件决定。从某种意义上来说，GPU、TPU 与 LPU 的区别并不仅仅是硬件设计上的区别，更是“运行时调度”与“编译期规划”两种思想的区别。

以目前最主流的 PyTorch 为例，当我们编写 `y = torch.matmul(a, b)` 这样一行代码时，程序实际上距离硬件执行还有非常遥远的距离。首先，PyTorch 会将这一操作转换为计算图中的一个节点。计算图本质上是一种有向无环图，用于描述张量之间的依赖关系——矩阵乘法必须等待输入张量准备完成，而后续的 LayerNorm 又必须等待矩阵乘法结束。计算图最重要的作用并不是执行计算，而是帮助编译器理解哪些算子可以融合、哪些中间结果可以复用、哪些内存可以提前释放、哪些计算能够并行执行。例如 `y = relu(matmul(a,b)+bias)` 对于开发者来说只是三步操作，但对于编译器来说，MatMul、Add 和 ReLU 完全有可能被融合成一个更大的 Kernel，这样中间结果就不需要频繁写回显存再重新读取，从而减少内存带宽压力。这也是为什么现代深度学习框架越来越强调图优化的原因。

然而需要注意的是，即使进行了计算图优化，GPU 的执行过程仍然具有很强的动态特性。计算图解决的是“做什么”的问题，而 GPU 真正需要解决的是“什么时候做、谁来做、在哪里做”的问题。当 Kernel 被提交到 GPU 后，CUDA 编译器会首先把高级代码编译成 PTX 中间表示，再由 NVIDIA Driver 在运行时进一步生成具体架构对应的机器码。随后 Kernel 被划分为大量 Thread Block，每个 Thread Block 会被动态分配到某个 SM 上执行。此时开发者通常只会指定 grid_size 和 block_size，而不会指定 Block 1 去 SM 37、Block 2 去 SM 52 这类具体映射——这些决策全部由运行时完成。换句话说，程序员实际上是在向 GPU 下发一个相对宽泛的任务，即启动这么多线程把这些数据处理完。至于具体哪些线程运行在哪些 SM 上，哪些 Warp 被优先调度，哪些数据被保留在 Cache 中，很多时候连编译器本身也无法提前确定。因此 GPU 内部必须依赖 Warp Scheduler、Scoreboard、Cache Controller、Memory Coalescing 和 Dynamic Dispatch 等大量运行时机制来不断做出调度决策。

这种设计带来了极高的灵活性。同一份 CUDA 程序既可以运行在消费级 RTX 5090 上，也可以运行在拥有数百个 SM 的 B200 上。但代价同样明显——由于许多决策是在运行时完成的，实际执行过程中会不断出现 Cache Miss、Warp Divergence、Memory Contention、Synchronization Stall 和 Kernel Launch Overhead 等各种不确定性。这些因素都会导致 GPU 的实际利用率与理论峰值之间出现明显差距。即使是同一个模型，在不同 batch size、不同数据分布甚至不同服务器环境下，都可能出现截然不同的性能表现。因此 GPU 更像是一种由运行时不断寻找最优执行路径的系统，计算图能够提供一定程度的规划，但无法彻底消除运行时的不确定性。

TPU 的软件栈则走向了完全不同的方向。如果说 GPU 的核心思想是尽可能让硬件在运行时做出最优决策，那么 TPU 的思想就是尽可能不要在运行时做任何决策。目前 TPU 最主流的软件栈是 JAX 经过 XLA 编译器到达 TPU Runtime 最终驱动 TPU 硬件的层次结构。与 PyTorch 更偏动态执行不同，JAX 的设计从一开始就强调函数式编程。当开发者使用 `jax.jit()` 时，程序首先会被 Trace，随后生成 HLO （High Level Optimizer）中间表示，可以把 HLO 理解为 TPU 世界中的一种中间语言，它位于 Python/JAX 代码与最终 TPU 指令之间，负责将神经网络转换成编译器能够分析和优化的数据流图。相比最终机器指令，HLO 仍然保留了矩阵乘法、Reduce、Transpose、Attention 等高层张量操作，因此编译器能够理解整个模型的计算逻辑，而不仅仅是一串底层指令。，此时 XLA 编译器开始接管整个计算过程。与 GPU 编译器主要优化单个 Kernel 不同，XLA 看到的是完整计算图，它不仅知道有哪些矩阵乘法，还知道哪些张量什么时候产生、什么时候被消费、哪些数据需要跨设备通信、哪些计算可以重叠执行。因此 XLA 不只是编译器，某种意义上它更像一个全局资源规划器。在编译过程中，算子融合、内存分配、DMA 搬运、Collective Communication 和 Tensor Sharding 都会被提前规划。最终生成的并不是一个等待运行时调度的程序，而是一张已经安排好的执行时间表。

对于 TPU 而言，数据从 HBM 到 VMEM 再到 MXU 之间的搬运时机通常已经在编译阶段确定。某个 Tensor 第几个周期开始加载、第几个周期进入 MXU、第几个周期产生结果、第几个周期发送到另一颗 TPU，理论上都可以提前知道。因此 TPU 的运行时非常轻量，它更多是在执行一份已经规划好的数据流脚本，而不是像 GPU 一样不断做出新的调度决策。这种设计带来的最大收益是确定性——同一个模型、同一份输入、同一个 TPU Pod，每次执行时的数据流几乎完全一致，缓存命中率、通信模式、计算顺序都不会出现明显波动。因此 TPU 的硬件利用率通常更加稳定。Google 在公开资料中多次展示过超过 60% 甚至 70% MFU(Model FLOP Utilization) 的训练案例，而在一些经过高度优化的内部训练任务中，整体利用率甚至能够超过 90%。当然，这种确定性也伴随着代价，因为一旦程序中出现 Dynamic Shape、数据依赖分支或不规则控制流，编译器能够发挥的空间就会迅速下降。某些在 GPU 上非常自然的代码，在 TPU 上则需要重新组织成静态数据流形式。从某种意义上来说，TPU 并不是在执行程序，而是在执行编译器提前规划好的数据流。

如果说 TPU 已经尽可能减少运行时决策，那么 LPU 则几乎完全消灭了运行时决策。Groq 的软件栈核心思想非常简单：所有能够提前确定的事情，都必须在编译阶段确定。编译器不仅负责生成指令，还负责规划整个芯片的数据流网络。模型中的每一个 Tensor 位于哪块 SRAM、什么时候移动、经过哪些计算单元、什么时候离开芯片，全部提前固定。因此 LPU 不再需要 GPU 那样复杂的运行时调度器，也不需要 TPU 中相对独立的 Runtime 层。编译完成之后，整个模型就像一条已经设计完成的流水线，数据只需要按照既定路线流动即可。这也是为什么 Groq 经常强调确定性执行——因为对于 LPU 来说，理论上每一次运行都应该产生完全相同的执行轨迹。

从 GPU 到 TPU 再到 LPU，可以明显看到一个趋势：硬件利用率越来越高，运行时的不确定性越来越低，而编译器承担的责任则越来越重。GPU 主要依赖运行时调度，TPU 主要依赖编译期规划，LPU 则几乎完全依赖编译器生成的数据流网络。这种变化的背后，其实对应着整个 AI 硬件行业的一条主线——越来越多的复杂性正在从硬件运行时转移到编译器，而编译器也正在逐渐成为决定 AI 系统性能的核心组成部分。



## 三、GPU 与 TPU 的互联拓扑差异

GPU 与 TPU 除了在芯片架构和软件栈上存在巨大差异之外，它们在大规模组网方式上的区别其实同样深刻。事实上，当模型规模来到数百亿甚至数万亿参数之后，决定训练速度的往往已经不再是单颗芯片本身的算力，而是这些芯片之间交换数据的能力。从结果上来看，GPU 和 TPU 最终都能够支撑超大规模模型训练，GPT-4、Llama、Gemini、Claude 等模型都运行在由数千甚至数万颗加速器组成的集群上，但如果继续向下观察，就会发现两者对于网络的理解几乎是完全不同的。

GPU 的组网方式本质上更接近传统数据中心网络，采用一种多级交换网络的结构。在单机内部，多张 GPU 首先通过 NVLink 相互连接。以 H100 为例，每颗 GPU 拥有 18 条第四代 NVLink，总双向带宽达到 900 GB/s，而 Blackwell B200 则进一步提升到了 1.8 TB/s。多个 GPU 再通过 NVSwitch 组成一个统一的 NVLink 域，使得任意两张 GPU 都能够通过交换机直接通信。继续向外扩展时，多个 GPU 节点会通过 InfiniBand 或 RoCE 网络连接到更大的集群中，这一层通常被 NVIDIA 称为 Scale-Out Network，而 NVLink 域内部则被称为 Scale-Up Network。从网络拓扑角度来看，这是一种典型的多级 Fat-Tree 或 Clos 结构，数据包从源 GPU 发出之后，会经过若干级交换机转发，最终到达目标 GPU，依次经过 NVSwitch、Leaf Switch、Spine Switch，再到对端的 Leaf Switch 和目标 GPU。因此在 GPU 集群中，任意两个 GPU 理论上都能够互相通信，区别只在于它们是否位于同一个 NVLink 域、是否跨节点、是否跨机柜、是否跨更大的 SuperPod，而这些因素会直接影响通信路径上的跳数以及可用带宽。

这种交换网络最大的优势是灵活。网络中的任何 GPU 都可以直接向任何 GPU 发送数据，因此对于 MoE、AllToAll、Parameter Server 等通信模式十分友好，但代价同样明显。随着集群规模扩大，交换机数量会迅速增长，尤其是在追求全二分带宽的情况下，高端 InfiniBand 交换机和光模块本身就会成为整个系统中极其昂贵的一部分。因此 GPU 的扩展本质上是在不断构建更大的交换网络。

TPU 则走向了另一条几乎完全不同的路线。TPU 从设计之初就没有采用传统交换网络，而是选择了一种规则化的邻居互联结构，Google 将其称为 ICI（Inter-Chip Interconnect）。在 TPU v2、v3、v5e 以及 Trillium（v6e）中，每颗 TPU 通常只与四个方向上的邻居直接连接，形成二维 Torus 网络；而在 TPU v4 与 TPU v5p 中，则进一步扩展为三维 Torus，每颗 TPU 与六个方向上的邻居直接连接。这意味着每颗芯片只需要维护有限数量的物理链路，无论整个集群扩展到多大规模，单颗 TPU 所需的网络接口数量几乎保持不变。但这种设计也意味着 TPU 并不存在 GPU 那种通过交换机实现的“一跳直达”——如果两颗 TPU 并非邻居，那么数据必须经过中间 TPU 逐跳转发。从传统网络工程角度来看，这似乎是一种效率较低的设计，但 Google 的思考方式并不是让任意节点之间通信尽可能方便，而是让大规模张量通信尽可能高效。
![TPU组网示意图]({{ '/assets/images/notes/TPU-network.png' | relative_url }})
*图 5：TPU组网示意图*
因为在 Transformer 训练过程中，大部分通信其实并不是随机流量，更多时候发生的是 AllReduce、ReduceScatter、AllGather 以及 Tensor Parallel 所需的 Collective 操作，这些通信模式高度规则化。对于这类通信而言，规则 Torus 网络反而具有非常高的带宽利用率。更重要的是，TPU 的链路数量不会随着集群规模增长而增加，因此理论上可以持续扩展到极大的规模，而不会像交换网络那样面临交换机端口数量和成本的指数增长问题。Google TPU v4 的一个完整 SuperPod 达到了 4096 颗 TPU 的规模，而 TPU v5p 则进一步扩展到超过 8000 颗 TPU。为了构建如此巨大的 Torus 网络，Google 引入了 OCS（Optical Circuit Switch，光路交换机）。需要指出的是，OCS 与传统 InfiniBand 交换机并不相同，它并不会像交换机那样实时转发数据包，而是在更高层级上重新配置 TPU Torus 的物理连接关系。因此 TPU 的通信本质上仍然是邻居通信，只不过这些邻居关系可以通过光交换网络重新组织。

这也是 TPU 网络与 GPU 网络最大的区别之一：GPU 依赖强大的交换机来完成任意节点之间的通信，而 TPU 更倾向于通过规则拓扑和邻居转发来获得可扩展性。两种方案各有明显优劣——GPU 网络更加灵活，对于复杂通信模式支持更好，也更符合传统分布式系统的设计习惯；TPU 网络则更加接近一种大规模矩阵计算机，它牺牲了一部分网络自由度，但换来了更低的成本、更简单的布线方式以及更容易扩展到超大规模集群的能力。某种意义上来说，这也是 GPU 与 TPU 整体设计哲学差异的延续：GPU 希望构建一个足够通用的计算平台，因此网络也追求通用性和灵活性，TPU 则从一开始就假设自己的目标是大规模张量计算，因此整个网络拓扑也围绕张量通信模式进行设计。从硬件架构、软件栈到集群网络，两者实际上都在沿着同样的方向做出取舍——究竟应该保留多少通用性，又应该为了效率牺牲多少灵活性。

<!-- ## 五、GPU 与 TPU 的利用率差异

理论峰值算力是一个容易被放大讨论的数字，但对实际使用者来说，真正重要的指标是模型 FLOP 利用率（MFU），即有多少理论算力最终稳定地用在了矩阵乘法和注意力计算上。

GPU 在这一点上长期面临挑战。大规模训练中，相当一部分算力实际上被通信等待、同步屏障、kernel launch 延迟、数据加载流水线断流以及运行时调度不确定性所消耗。行业内公开的经验是，经过深度优化的 GPU 集群能够将 MFU 稳定在 30% 到 50% 之间，便已属相当不错的成绩。即使是机内 NVLink 带宽，研究也发现其实际利用率因流量偏斜、路径不均衡和 NCCL 路由低效等因素，经常未能跑满标称峰值。

TPU 因为其编译期完全确定性的数据流设计，在大规模矩阵运算中天然具备利用率的优势。流水线预排、通信与计算的重叠、算子融合等均提前规划好，runtime jitter 被压缩到极低。JAX 社区与 Google 公开的技术资料显示，TPU 在典型训练负载上能够达到 60%–70% 以上的 MFU，部分内部大模型训练案例中，整个 TPU Pod 的硬件利用率甚至超过 90%。对于拥有成千上万颗芯片的超大规模集群而言，"少一点运行时混乱"往往比"多一点理论 FLOPS"更具实际意义。当然，这种高利用率的前提是 workload 必须足够规整——一旦计算图中出现大量动态 shape 或复杂控制流，静态编译的优势就会显著降低。

LPU 则把利用率问题推到了最极端：编译器对全局执行路径的绝对掌控，使得硬件在推理过程中几乎没有空闲周期，能效比可达 GPU 的 10 倍。 -->

## 结语

GPU、TPU、LPU 并非简单的迭代替代关系，而是 AI 时代计算架构重新分化的产物。GPU 在通用并行计算平台的位置上不断吸收专用计算能力，TPU 在矩阵数据流机器的轨道上追求编译期确定性和超大规模效率，LPU 则将推理流水线的固定化推向极致。而 NVIDIA 的下一代设计也在逐渐向更规则的数据流和更紧密的互联拓扑靠拢，TPU 则在不断提高对动态特性的支持，专用与通用之间的边界正在变得模糊。未来 AI 基础设施竞争的核心，已经不是谁的理论算力更高，而是谁能让整个系统的数据流、内存、互联与计算协同运转得更高效。而这，或许才是接下来十年真正的决定性变量。
